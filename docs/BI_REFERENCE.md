# BI 参考与 EchoMerch 落地

这份记录用于吸收成熟 BI 产品的交互思路，不把 EchoMerch 做成通用 BI 平台。

## 值得借鉴的模式

### 1. 全局筛选器

成熟 BI 产品通常把日期、店铺、渠道、商品等筛选器放在仪表盘层，并让多个图表共享筛选条件。

EchoMerch 当前先统一日期区间。后续按这个顺序扩展：

1. 店铺/数据空间。
2. 商品或商品组。
3. 流量来源。
4. 推广计划。

每增加一个筛选条件，都要同步更新 API 参数、数据口径和页面 URL 状态。

### 2. 从汇总到明细

用户看到 Top 商品或流量来源后，下一步通常是点击进入明细，而不是重新手动筛选。

EchoMerch 的下钻链路建议为：

```text
概览指标
  -> 商品/来源排行
    -> 日期趋势
      -> 原始记录或数据质量说明
```

第一阶段可以只做页面路由和筛选条件传递，不急着暴露原始订单。

### 3. 指标与数据集分离

图表不是数据模型。建议后端逐步形成：

- 数据集：店铺日表、商品日表、流量来源表、推广计划表。
- 指标：支付金额、访客、买家、支付转化率、推广花费、ROI。
- 维度：日期、商品、来源、计划。
- 口径说明：单位、是否含退款、数据更新时间、空值处理。

这样后续接入抓包接口时，先把平台字段映射到统一指标，不把平台字段直接散落到 Vue 页面。

### 4. 图表事件标注

趋势线需要能解释变化原因。后续可以叠加：

- 大促/活动日期。
- 价格或优惠券调整。
- 推广计划启停。
- 数据同步延迟。
- 人工记录的经营事件。

事件先作为只读标注，不触发任何平台动作。

### 5. 能力开关与权限边界

复杂 BI 系统会把能力、权限和数据访问分开。EchoMerch 当前用 `/api/v1/system/capabilities` 明确：

- 哪些模块已启用。
- 哪些模块暂时关闭。
- 当前是否只读。
- 当前阶段的安全规则。

后续加入批量建券、脚本任务时，应该继续沿用这个能力边界，而不是仅靠前端隐藏按钮。

## EchoMerch 的分阶段路线

### Phase 1：可靠看数

- 日期区间筛选。
- 店铺、商品、来源、推广四类基础视图。
- 数据新鲜度。
- 空态、错误态、只读状态。

### Phase 2：可解释分析

- 指标口径页。
- 排行到趋势的下钻。
- 事件标注。
- 数据质量和同步延迟提示。

### Phase 3：可控任务

- 任务预览。
- 二次确认。
- 幂等键。
- 逐条结果、失败重试、审计日志。

### Phase 4：平台适配

- Reqable 抓包样本。
- 脱敏后的接口契约。
- 独立 worker 或平台适配器。
- 仅在明确授权和风控边界内接入动作。

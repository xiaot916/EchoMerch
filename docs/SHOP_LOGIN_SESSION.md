# 店铺登录与会话设计

## 已确认的登录链路

`loginmyseller.taobao.com` 是千牛入口页，页面再加载 Havana 登录组件
`havanalogin.taobao.com/mini_login.htm`。组件支持账号密码、短信和手机扫码，
二维码通过登录接口动态生成并轮询状态；它不是一个可以长期复用的静态图片地址。

登录成功后，淘宝系 SSO 会在浏览器 Profile 中建立店铺域和业务域的 Cookie。生意参谋、
CPS、品销宝、数据银行、阿里妈妈等域名仍然可能各自做一次跳转或 bootstrap，不能把
生意参谋的 `jycmToken` 当作所有平台的全局登录凭证。

## 当前实现

- 采集设置提供“千牛店铺登录”状态卡片。
- 点击“打开千牛登录”只会复用现有标签页；没有时通过 CDP HTTP 接口直接创建目标页，
  不再先显示 `about:blank`。
- 登录状态接口只返回状态、域名和无敏感信息的页面地址，不返回 Cookie、Token、二维码内容。
- 店铺目录复用已有 `stores` 表；首次成功采集后，店铺会显示在设置页。
- 采集浏览器启动参数包含 `--remote-allow-origins=*`，允许 DrissionPage 正常接管页面。

## 不保存账号密码的原因

淘宝登录会结合设备指纹、风控校验、滑块、短信或扫码确认。把密码写入 SQLite 或环境变量
不能稳定实现自动登录，同时会扩大凭据泄露面。当前方案让 Chrome Profile 负责加密保存登录
Cookie，系统只读取内存中的会话完成报表请求。

## 多店铺扩展方案

后续需要多账号并行时，为每个店铺增加独立的 Chrome Profile 和调试端口，数据库只保存：

- 店铺 ID、店铺名称、平台主体 ID；
- Profile 标识和端口；
- 最近一次登录状态、最近一次成功采集时间；
- 是否需要用户重新扫码。

不要在店铺表中增加明文密码字段。若确实需要托管密码，应接入 Windows Credential Manager
或 DPAPI，前端只能写入和轮换，后端永不回显；默认仍建议扫码登录。
